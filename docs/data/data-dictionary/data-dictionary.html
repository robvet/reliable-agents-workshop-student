What this document adds

The field lists below are the easy part. What matters more for a demo, a workshop, or an SME reviewing this schema is what each table means in the business, how a real outage moves through it end to end, and where a reasonable-looking join produces a confidently wrong answer.

  • Every table gets a plain-English purpose statement — what it is the record of, and what it explicitly is not.
  • Every field gets a semantic note — not just its SQL type, but what it represents in the operation of the grid and how the app actually uses it.
  • The restoration lifecycle is diagrammed — how an outage moves from reported to restored, and which table owns each step.
  • A query cookbook for the joins people get wrong most often on this schema.
  • Assumptions are labelled as assumptions. Where the schema does not settle a question, this document says so rather than inventing an answer.

The restoration lifecycle

An outage moves through four statuses, in order, never skipping a step. This is enforced in code (OutageLifecycleService), not just a convention — outage_status_log is the append-only ledger of every transition, and the latest row per outage is its current status (see the outage_current_status view below). The exact same status also writes through to grid_assets.status on the affected asset, so "what's wrong with this transformer right now" never needs a join.

A fifth, administrative status CLOSED exists in the schema and in outage_status_log, but the UI no longer surfaces it as an operator action — RESTORED is treated as the terminal, "done" state a person needs to act on. CLOSED still exists purely so a new outage can be opened again later on the same asset.

How an outage actually enters the system

Short answer: as an outage, tied to exactly one event. The outages row is the record of record — it owns the asset and the impact numbers. events is the primitive underneath it: any occurrence, tiny or huge, is one row there, and it does not know about outages at all. A one-off "tennis shoe on a line" incident still gets its own one-row event; a major storm gets one shared event that many outages point back to.

Step 1 · the incident
events

Any occurrence — a storm, a vehicle strike, a single equipment failure. Severity (LOW/MEDIUM/HIGH) is judged per event, not derived from its type.

Deliberately out of scope

There is no customer or billing domain in this schema. An earlier version of this app had customers, outage_reports, and meter_readings tables; they were removed on purpose. This app is an internal grid-operations tool — detection, outage management, restoration — and customer data structurally belongs in a separate system (a CIS), not co-located here. If a future feature genuinely needs "who is affected", the service_locations/meters topology already gets you to a premise/meter count without a customer table (see the query cookbook).

⚡Assets & Topology

grid_assets

The backbone

Every piece of physical grid equipment — substations, feeders, transformers — is one row here, self-joined into a hierarchy via parent_asset (substation → feeder → transformer). This is the one table almost every other table eventually points back to.

FieldTypeKeyWhat it means
asset_idvarchar(36)PKStable identifier used everywhere else that refers to this asset.
asset_typevarchar(50)SUBSTATION / FEEDER / TRANSFORMER. Determines this asset's level in the hierarchy.
asset_namevarchar(120)Human-facing label (e.g. "Feeder-100"). Prefer this over the UUID in any answer shown to a person.
parent_assetvarchar(36)FK → grid_assetsSelf-referencing: a transformer's parent is a feeder; a feeder's parent is a substation. NULL for a substation (top of the tree).
voltage_kvdoubleNameplate voltage rating.
rated_capacity_kvadoubleNameplate capacity; the load/health hook for future capacity-stress features.
install_datedateWhen the asset was placed in service.
asset_conditionvarchar(30)Lifecycle state, not outage state: INSTALLED / MAINTENANCE / RETIRED. Answers "is this asset commissioned and in service?" — unrelated to whether it currently has a problem.
statusvarchar(30)Real-time outage state: REPORTED / CONFIRMED / CREW_ASSIGNED / RESTORED / NORMAL. Kept in sync automatically on every outage transition, so a status question about one asset never needs a join to the outage tables.
latitude / longitudedoubleMap coordinates — what the Asset Map plots.
regionvarchar(60)Geographic grouping used for regional questions ("outages in the North region").

The two status-like fields, side by side

  • asset_condition and status answer two completely different questions and must never be conflated in an answer. A transformer can be INSTALLED (lifecycle) and have status CREW_ASSIGNED (an active outage) at the same time — that is not a contradiction, it is the normal case.
  • Never say an asset is "active"/"healthy" in the same sentence as an open outage — that reads as a contradiction to a human even though the two fields are orthogonal in the schema.

service_locations

Where power is delivered

A physical premise (residential or commercial) fed by exactly one transformer. This is the bridge between the grid's topology and the meters attached to it — the table you join through to answer "how many premises does this outage affect?"

FieldTypeKeyWhat it means
location_idvarchar(36)PKStable identifier for this premise.
address / city / state / zipvarcharHuman-facing location, not used for any grid logic.
location_typevarchar(20)RESIDENTIAL or COMMERCIAL.
latitude / longitudedoubleIndependent coordinates for this premise (not derived from its transformer's).
regionvarchar(60)Inherited from the serving transformer at creation time.
transformer_idvarchar(36)FK → grid_assetsThe one transformer that serves this premise. This is the join that connects topology to metering.

meters

The last physical hop

One physical meter installed at a service location. Topology-only in this schema — there is no meter-reading/usage table here by design (kept for a future "show meters affected by this outage" map feature).

FieldTypeKeyWhat it means
meter_idvarchar(36)PKStable identifier for this meter.
location_idvarchar(36)FK → service_locationsWhich premise this meter is installed at.
meter_typevarchar(30)e.g. SMART METER, LEGACY AMR.
communication_typevarchar(20)e.g. RF MESH, PLC, CELLULAR.
install_datedateWhen the meter was installed.
statusvarchar(20)Meter device status: ACTIVE / INACTIVE / FAULTED. Not related to grid_assets.status — this is about the meter's own health, not an outage.

Derived view: asset_meter_map

Pre-joins the full chain — substation → feeder → transformer → service_location → meter — into one flat row per meter, so "which meters lie beneath asset X" is a single WHERE clause instead of a hierarchy walk. Not wired to any live feature yet; exists so the design isn't lost when the map feature is built.

🌪️Events

event_types

Extensible vocabulary

A lookup of event categories — STORM, VEHICLE, FIRE, EXPLOSION, and whatever else gets added over time. Not a fixed enum; new categories can be added as rows without a schema change.

FieldTypeKeyWhat it means
event_type_codevarchar(30)PKe.g. STORM, VEHICLE.
descriptionvarchar(120)Human-facing label for the category.

events

The primitive

Any occurrence — tiny or huge — is one row here. This table deliberately does not know about outages; it is the "what happened" record that one or more outages can later attach to.

FieldTypeKeyWhat it means
event_idvarchar(36)PKStable identifier for this occurrence.
event_type_codevarchar(30)FK → event_typesWhat kind of occurrence this was.
namevarchar(120)Human-facing label, e.g. "North Region Storm".
severityvarchar(20)LOW / MEDIUM / HIGH. Judged per event, never derived from event_type_code — a STORM can be LOW severity, a single VEHICLE strike can be HIGH.
regionvarchar(60)Where the event occurred.
start_timetimestampNOT NULL — every event has a start.
end_timetimestampNULL means still ongoing. There is no literal "status" column on events — "is this event active?" is derived from whether end_time is NULL, not stored as a flag.

event_asset_threat

Dormant — schema only

Which assets a given event (e.g. a simulated storm) currently threatens — a proximity warning, and a genuinely different concept from an outage: an asset can be threatened with no outage yet, or have an outage with no active threat.

FieldTypeKeyWhat it means
threat_idbigserialPKSurrogate key.
event_idvarchar(36)FK → eventsThe threatening event.
asset_idvarchar(36)FK → grid_assetsThe threatened asset.
detected_at / cleared_attimestampNULL cleared_at means still currently threatened.

Nothing writes to this table today

No ORM model, service, or agent populates it — the write path (a future StormThreatService) was never built. Kept intentionally, not dead weight: the schema exists so the design isn't lost if the feature is picked up later.

🚨Outages

outages

Record of record

Links one event to one impacted asset. Deliberately thin: no status column here at all — status is derived from outage_status_log, never duplicated onto this row.

FieldTypeKeyWhat it means
outage_idvarchar(36)PKStable identifier for this outage.
event_idvarchar(36)FK → eventsNOT NULL — every outage belongs to exactly one event, even a standalone one-off incident that gets its own one-row event.
asset_idvarchar(36)FK → grid_assetsThe impacted asset. Nullable if the asset is later removed.
impact_countintegerHow many premises/points are affected.
impact_magnitudedoubleVolume/load impact (e.g. MW) — not a dollar figure, not a customer count.

outage_status_log

The audit trail

Append-only history: one row per status transition for one outage. This is the source of truth for an outage's current status — never a column on outages itself.

FieldTypeKeyWhat it means
log_idbigserialPKSurrogate key.
outage_idvarchar(36)FK → outagesNOT NULL, cascades on delete.
event_typevarchar(30)REPORTED / CONFIRMED / CREW_ASSIGNED / ETR_UPDATED / RESTORED / CLOSED. This is the ledger's own event-type vocabulary — a different, unrelated concept from the events table despite the shared word "event".
from_status / to_statusvarchar(20)The transition this row records. to_status on the latest row per outage is that outage's current status.
etrtimestampEstimated time of restoration. Never populated in this app today — no generator or live code path writes to it, so it will always read NULL against current data.
notetextFree-text field notes (e.g. a crew's on-site observation), optionally used to trigger severity-escalation review.
event_timetimestampNOT NULL, defaults to now(). When this transition happened.

Derived view: outage_current_status

SELECT DISTINCT ON (outage_id) ... ORDER BY outage_id, event_time DESC — the latest ledger row per outage. Query this view for "what is this outage's status right now?" rather than hand-rolling the same DISTINCT ON every time.

👷Crews & Restoration

crews

Who responds

Field crews available for outage response and work orders.

FieldTypeKeyWhat it means

crew_namevarchar(100)Human-facing label.
crew_typevarchar(40)DISTRIBUTION / EMERGENCY_RESPONSE / METERING / TRANSMISSION. Only DISTRIBUTION and EMERGENCY_RESPONSE crews are eligible for outage-restoration assignment.

work_orders

The dispatch record

Created the first time an outage reaches CREW_ASSIGNED — the record that ties a crew to an outage and an asset, and tracks the restoration job itself through to completion.

FieldTypeKeyWhat it means
work_order_idvarchar(36)PKStable identifier for this work order.
outage_idvarchar(36)FK → outagesWhich outage this dispatch responds to.
asset_idvarchar(36)FK → grid_assetsThe asset being worked on.
crew_idvarchar(36)FK → crewsThe assigned crew. Same crew stays assigned across repeat updates to the same outage — a new work order is not created every time.
wo_typevarchar(30)e.g. OUTAGE RESTORATION.
priorityvarchar(10)LOW / MEDIUM / HIGH / CRITICAL.
statusvarchar(20)OPEN / ASSIGNED / IN_PROGRESS / COMPLETED / CANCELLED. Unrelated to grid_assets.status or the outage's own status — this is the work order's own progress.
created_date / scheduled_date / completed_datetimestampThe job's own timeline.
estimated_hours / actual_hoursdoublePlanned vs. actual effort.

Query cookbook

1. All currently open outages, with the affected asset and crew

The everyday operator question. Joins through the current-status view so it never needs a hand-rolled DISTINCT ON.

SELECT  o.outage_id, ga.asset_name, ocs.status, ocs.status_since,
        c.crew_name
FROM    outages o
JOIN    outage_current_status ocs ON ocs.outage_id = o.outage_id
JOIN    grid_assets ga            ON ga.asset_id  = o.asset_id
LEFT JOIN work_orders wo         ON wo.outage_id = o.outage_id
LEFT JOIN crews c                ON c.crew_id    = wo.crew_id
WHERE   ocs.status NOT IN ('RESTORED', 'CLOSED');

2. Meters downstream of a given asset (any level)

Uses the pre-joined asset_meter_map view instead of a recursive parent-walk — one flat WHERE clause regardless of whether the outaged asset is a substation, feeder, or transformer.

SELECT m.meter_id, sl.address, sl.latitude, sl.longitude
FROM   asset_meter_map amm
JOIN   service_locations sl ON sl.location_id = amm.location_id
JOIN   meters m             ON m.meter_id     = amm.meter_id
WHERE  amm.substation_id = :asset_id
   OR amm.feeder_id     = :asset_id
   OR amm.transformer_id = :asset_id;

3. Full status history for one outage, with ETR if ever set

Reads the append-only ledger directly — use this when the audit trail, not just the current state, matters.

SELECT event_type, from_status, to_status, etr, note, event_time
FROM   outage_status_log
WHERE  outage_id = :outage_id
ORDER BY event_time;

4. Outages by severity, via their event

Severity lives on events, not on outages — do not look for a severity column on the outage row itself.

SELECT o.outage_id, e.name AS event_name, e.severity
FROM   outages o
JOIN   events e ON e.event_id = o.event_id
WHERE  e.severity = 'HIGH';

5. Crew workload by region

Crew availability is entirely independent of outage/asset status — a common mistake is joining this to grid_assets.status, which has no relationship to it.

SELECT region, status, COUNT(*) AS crews
FROM   crews
GROUP BY region, status
ORDER BY region, status;

Instructions for a natural-language-to-SQL agent

  1. grid_assets has two status-like fields that must never be conflated: asset_condition (lifecycle: INSTALLED/MAINTENANCE/RETIRED) and status (real-time outage state: REPORTED/CONFIRMED/CREW_ASSIGNED/RESTORED/NORMAL). A question about whether an asset "has a problem right now" is answered by status alone — no join required.
  2. An outage's current status is not a column on outages — join outage_current_status (or query outage_status_log directly) to get it.
  3. events has no status column — derive "active" vs. "ended" from whether end_time is NULL, do not search for a literal status field.
  4. When a question asks which assets/meters are affected by an outage, use asset_meter_map instead of hand-rolling a parent_asset recursive walk.
  5. There is no customer or billing table in this schema. Do not invent one, and do not answer "how many customers are affected" as anything other than a premise/meter count via service_locations/meters.
  6. Match text/categorical filters case-insensitively (ILIKE) — stored values may differ in case from how a user phrases them.

Conventions

  • Every primary key is a varchar(36) UUID string, except two append-only ledger tables (outage_status_log, event_asset_threat) which use bigserial.
  • Every "why did this happen" question (outage status, event severity) is answered by a dedicated field on the record closest to the fact, never inferred from a join across domains.
  • Anything marked dormant above has real schema and real foreign keys, but no code path writes to it yet — it exists so a future feature's design isn't lost, not because it's in active use.
